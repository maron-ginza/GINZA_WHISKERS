# Discover GINZA Media System — 技術選定

**ステータス：承認済み（2026-07-21）**。CMS＝Payload CMS（自己ホスト）、
フロントエンド＝Astro、ホスティング＝Railway／Cloudflare R2／Cloudflare
Pages、AI生成＝Anthropic APIで確定。確定事項はCLAUDE.md第6章・第12章に
反映済み。

**位置づけ**：CLAUDE.md第6章の「技術選定はデザイン確定後」という合意に
基づくセッション。デザイン（第5章）・コンテンツモデル（`CONTENT_MODEL.md`）
が確定した状態を前提に、CMS・フロントエンド・ホスティングを決定した。

**判断基準（要件から逆算）**：
1. `CONTENT_MODEL.md`のArticle/Source/ImageAsset/Tagスキーマ（状態遷移・
   承認ログ・資料番号・バイリンガル）をそのまま表現できるか
2. 承認キュー・編集長レビューUIを**自作せずに済む**か（10月ローンチに
   向けて自作範囲を減らせるほど有利）
3. AI記事生成・X/Instagram API連携をフックできる余地があるか
4. 「数十年続く文化アーカイブ」という第5章の位置づけに対し、データを
   自分たちで所有できるか（SaaSベンダー依存のリスク）
5. 小規模チームで長期運用できる保守負荷か
6. Root第6章の原則：依存を増やすなら「なぜ自前で持たないのか」を
   一言で説明できること

## 1. コンテンツ基盤（CMS / バックエンド）

| 候補 | 概要 | 評価 |
|---|---|---|
| **Payload CMS**（自己ホスト・Node/TypeScript・Postgres） | コードでコレクション定義するヘッドレスCMS。下書き/バージョニング/アクセス制御/ライフサイクルフックが標準搭載 | ◎ |
| Directus（自己ホスト・DB-first） | 既存DBスキーマからAPI・管理画面を自動生成。ノーコード自動化（Flows）も持つ | ○（次点） |
| Sanity / Contentful（SaaS） | 高機能なホスト型ヘッドレスCMS。リアルタイム共同編集が強み | △ |

**推奨：Payload CMS**

- `CONTENT_MODEL.md`のスキーマ（`status`の状態遷移、`accession_number`、
  `historical_period`、`translation_status`等）を、TypeScriptの
  コレクション定義としてほぼそのまま表現できる。
- 下書き→レビュー→承認→公開のワークフロー、承認ログ、ロールベースの
  アクセス制御が標準機能にあるため、**「承認キュー」「編集長レビューUI」を
  自作する必要がなくなる**（管理画面の設定作業に縮小できる）。
- `afterChange`等のフックで「承認された瞬間に資料番号を自動採番する」
  「AIで下書きを生成する」「X/InstagramへAPI送信する」といった処理を
  直接組み込める。
- 自己ホスト＝データを自分たちで所有する。「数十年続くアーカイブ」という
  位置づけ（第5章）に対し、SaaSベンダーの存続・値上げ・API仕様変更に
  引きずられない。オープンソースであり、Root第6章の「なぜ自前で持たないのか」
  にも「独自の承認ワークフロー・資料番号採番・AI連携フックを持つ必要が
  あり、汎用SaaSでは表現しづらいため」と説明できる。

Directusも同格の候補だが、コードファーストでのスキーマ定義・フック実装は
Payloadの方がこのプロジェクトの要件（複雑な状態遷移とAI/API連携フック）に
合う。Sanity/Contentfulは編集体験は優れるが、SaaS依存という点が
「長期アーカイブ」という自己定義と相性が悪いため今回は見送る。

## 2. フロントエンド（02サイト表示）

| 候補 | 概要 | 評価 |
|---|---|---|
| **Astro** | コンテンツ中心のサイト向け。デフォルトでJSをほぼ配信しない | ◎ |
| Next.js | 汎用的で強力だが、インタラクティブなアプリ向けの機能が中心 | △ |

**推奨：Astro**

- 02は「記事＋ギャラリーを読む」ことが主目的のアーカイブサイトであり、
  管理画面側の複雑な操作UIはPayloadの管理画面が担う。02自身に重い
  クライアントサイドの状態管理は不要。
- Astroはビルド時にほぼ静的なHTMLへ変換され、表示速度・SEOで有利
  （記事数が数千件に増えても表示性能が落ちにくい）。
- 多言語ルーティング（`/ja/...` `/en/...`）を標準機能として持ち、
  第7章のバイリンガル要件と相性が良い。
- Next.jsは強力だが02の要件に対してはオーバースペックであり、小規模
  チームの保守負荷を上げる。

## 3. ホスティング・インフラ

| レイヤー | 候補 | 推奨 |
|---|---|---|
| CMSバックエンド（Payload＋Postgres） | Railway / Render / Fly.io | **Railway**（マネージドPostgres込みでデプロイが簡単） |
| 画像ストレージ | Cloudflare R2 / AWS S3 | **Cloudflare R2**（S3互換API、転送量課金なし。画像点数が増え続けるアーカイブに有利） |
| フロントエンド配信 | Cloudflare Pages / Vercel / Netlify | **Cloudflare Pages**（Astro出力と相性が良く、無料枠が広い） |
| AI記事生成 | Anthropic API（Claude） | 既存のワークフロー（Claude Code）と地続きで運用できる |
| X / Instagram API連携 | Payloadバックエンドと同居する小さなワーカー処理 | 承認キューのステータス変更をトリガーに送信 |

R2を選ぶ理由：画像はアーカイブの中核資産であり、件数が今後数千件規模に
増えることを前提にしている（第5章）。転送量課金のないR2は、ギャラリー・
SNS書き出し（4.チャネル別バリアント）を含め長期的なコストを抑えやすい。

## 4. この選定で変わること（Phase 1残タスクへの影響）

`ARCHITECTURE_DRAFT.md`のPhase 1残タスクのうち、以下は**自作ではなく
Payloadの設定作業に縮小**できる：

- 画像管理基盤 → Payloadのメディアコレクション＋R2アダプタ設定
- 編集長レビューUI → Payload管理画面のドラフト/レビュー機能をそのまま利用
- 承認キュー → Payload管理画面のステータスフィルタ＋承認ログ機能を利用

一方、以下は引き続きカスタム実装が必要：

- AI記事生成パイプライン（Claude API呼び出し、6本柱・トーン原則を
  埋め込んだプロンプト設計、生成結果をPayloadへ書き込む処理）
- 情報収集の受け皿（ソース登録UI。Payloadの標準コレクションで代替可能か
  要検証、複雑なら軽量な専用画面を追加）
- 02サイト本体（Astroでの実装）
- X/Instagram配信ワーカー

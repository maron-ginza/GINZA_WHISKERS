## 1. シリーズ定義

- **シリーズ名称**：「銀座情報局 by GINZA WHISKERS」
- **コアフレーズ**：「旬の銀座を、毎日。」
- **読者向けの位置づけ**：Project 02 の内部名称は「AI GINZA EDITORIAL
  DESK」だが、note 等で読者に示すシリーズ名は「銀座情報局 by GINZA

- **既存シリーズ識別との関係**：`Articles.series`（`label` /
  `editionNumber`）はそのまま使う。日次「旬の銀座」記事の

  §20）。**TNS は独立したシリーズ名（Tokyo Nostalgic Soundtrack）を
  保持し、本シリーズ名に統合しない。**

## 2. シリーズの趣旨

銀座の新店・イベント・文化・街の変化を毎日収集し、GINZA WHISKERS の
編集視点で「今、知っておきたい銀座＝旬の銀座」を選び、意味づけして
届ける編集メディアとする。

**単なるイベント告知・店舗紹介・公式情報の転載にしない。** すべての
記事に、次の3つを編集価値として必ず加える。

1. **なぜ今なのか**（WHY NOW?）
2. **なぜ GINZA WHISKERS が選ぶのか**（EDITOR'S NOTE）
3. **読者がどう楽しめるのか**（次にどう楽しむか）

この方針は `CLAUDE.md` 第8章「読者接続の編集ロジック」（2026-08-21）・
Editorial Trust Layer 項目4（Fact と Editorial Note の分離）と同一で
あり、本節はそれを日次シリーズの必須要件として明文化したもの。

## 3. 記事冒頭の基本表現（マストヘッド）

### 3.1 基本形

```
銀座情報局 by GINZA WHISKERS
旬の銀座を、毎日。

銀座の新店、イベント、文化、街の変化から、
今だから知っておきたい銀座を
GINZA WHISKERS の編集視点で届けます。
```

### 3.2 運用ルール

- **1〜2行目（シリーズ名＋コアフレーズ）は毎記事に置く。**
- **3行目以降の説明文は、記事のボリューム・内容に応じて短縮・省略して
  よい。** 短文記事では1〜2行目のみ、または説明文を1文に圧縮する。
- Editorial Style Engine 項目2「長い挨拶から始めない」と両立させる
  ——マストヘッドは定型の看板であって挨拶ではない。マストヘッド直後の
  本文は、季節感・街の空気・今週性を短く述べてから本題に入る。
- 毎記事で同じ長い説明文を機械的に繰り返さない。

## 4. 記事基本構成（日次・単一トピック）

原則として以下を基本骨格とする。

| # | ブロック | 内容 |
|---|---|---|
| 1 | 銀座情報局 by GINZA WHISKERS（マストヘッド） | §3 |
| 2 | 旬の銀座（導入） | 今なぜこの銀座か。季節・街の空気・今週性を短く |
| 3 | **WHY NOW?** | なぜ今、この情報なのか（確認済みの会期・季節文脈に接地） |
| 4 | **EDITOR'S NOTE** | なぜ GINZA WHISKERS が選んだのか（Fact と分離） |
| 5 | 出典 | §7 の読者向け整形形 |
| 6 | 次にどう楽しむか | 読者の行動・体験につながる短い導線（1文・1アクション＝既存 `callToAction`） |

### 4.1 短文記事での省略

短文記事では、すべての見出しを強制しない。内容に応じて自然に統合・
省略してよい（例：WHY NOW? と EDITOR'S NOTE を1段落に統合、導入と
マストヘッド説明文をまとめる）。

### 4.2 内部情報を読者向け本文に出さない（angleSummary）

`angleSummary`（`generateMultiAngleArticleDrafts.ts`）は、生成制御・
内部編集用のフレーミング情報として扱い、**読者向け note 本文の見出し
として表示しない**。現在の `buildAngleArticleBlocks` は `angleSummary`
を h2 見出しへ出力しており、記事の主見出しとして不自然なメタ文
（例：「…を GINZA WHISKERS の編集視点で紹介する記事」）になる事例が
ある（Trial #53）。これは、生成用・内部用の文言がそのまま読者向け
本文に出てしまう問題であり、§7.1 の `[IMAGE:]` マーカーと同じ考え方で
防止する。マストヘッド（§3）・WHY NOW? / EDITOR'S NOTE を骨格の見出し
とする。

する（Editorial Trust Layer をそのまま適用）。

## 7. 内部マーカー・出典表記の読者向け整形

### 7.1 内部画像マーカー

`[IMAGE: アイキャッチ]` `[IMAGE: 見出し …]` などの内部制御表記は、
**note 転記用本文・公開本文に絶対に残さない。**

- 実画像を挿入できる場合 → 実画像へ置換
- 実画像がない場合 → **自動削除**（マーカー行を本文に残さない）
- 画像の配置意図は本文テキストではなく、パッケージのメタ情報
  （`note-draft.json` の `images[].placement` 等）で保持する

### 7.2 出典表記

内部ログ形式（`SOURCE: <名称>／確認: <日付>／<URL>`）を読者向け本文に
そのまま出さない。note 公開用は自然な表記へ整形する。

```
出典：銀座 蔦屋書店
公式情報を確認：2026-08-31
```

必要に応じて公式 URL をリンクとして付与する。`CLAUDE.md` 第8章
Editorial Style Engine 項目10 の読者向け表示形は本節の表記で更新する
（実装は §20）。

# 無料／有料コンテンツ設計

## 9. 基本原則

### 9.1 対象の2系統と無料／有料の考え方の違い（2026-08-31 follow-up・確定）

無料／有料化の考え方は **① 旬の銀座 と ② 収益化・注目テーマ × 銀座 で
同一にしない**（適用範囲の表を参照）。

| | ① 旬の銀座（5本） | ② 収益化・注目テーマ × 銀座（5本） |
|---|---|---|
| **無料記事** | 銀座のイベント・新店・文化・店舗・体験の**コンテンツ情報紹介**を基本とする（§10） | 9月Trial では原則置かない（5本すべて有料候補）。有料価値が成立しない記事のみ無料公開（§9.3） |
| **有料候補** | **「私だけの銀座時間」**（読者の銀座体験そのものを設計する）を**有力な有料候補として検証する**（§11、9月Trial） | **9月Trial 仮説：5本すべて原則「有料候補」。2層価格（A=100円 テーマ×銀座＝「理解」／B=300円 テーマ×旬の銀座×私だけの銀座時間＝「体験」）**（§9.3・§13.3） |

- ① の有料候補「私だけの銀座時間」は、**将来の GINZA UX体験（Root
  `CLAUDE.md` 第1章の Project 04、現在"未確認"）につながる Trial** として
  扱う。ここで cross-project の仕様を先取りしては作らない。
- ① について「旬の銀座の有料記事＝必ず散策ルート」とは**まだ固定しない**
  （§11）。
- ② の無料／有料は「未決定」から **9月Trial の2層価格仮説（100円／300円）**
  へ更新した（§9.3）。価格は本価格として固定せず、10月本運用前に見直す。
- ② B（300円）の「私だけの銀座時間」部分は将来の GINZA UX体験／Concierge
  の Prototype・需要検証（§18、Project 04 接続仕様は未確定）。

### 9.2 両系統に共通する原則

- 無料記事と有料記事の差は、**「文字数」や「情報量」ではなく、読者が
  得られる編集価値・判断価値・行動価値で作る**。
- **無料記事を意図的に薄くして、続きを有料に誘導する設計は禁止する**
  （Root 憲章第2章「非扇動的」・Editorial Trust Layer を適用）。
- **無料記事単体でも「読んでよかった」「今の銀座が分かった」という満足
  が成立することを必須とする。**
- 有料記事は、無料記事では得られない追加価値（選択・比較・組み合わせ・
  ルート設計・時間短縮・条件別最適化など。具体は系統ごとに §11・§13.2〜
  §13.3）を提供する。**有料価値が成立しない記事を、本数合わせのために
  有料化してはいけない**（§16.1）。
- 記事生成後の Paid Candidate 5軸評価（§13.1）と、**最終的な無料／有料
  判断はマロン**が行うことは、①②とも共通。

### 9.3 ② の無料／有料の棲み分け（2026-08-31 follow-up・9月Trial 仮説）

**9月Trial では ② の5本すべてを原則「有料候補」として扱う。** ただし
**有料価値が成立しない記事は無理に有料化しない**（§9.2、無料で公開）。

価格は次の **2層を9月Trial の仮説**とする（本価格として固定しない、§16）。

| 層 | 価格（Trial仮説） | 記事の型 | 読者が得るもの |
|---|---|---|---|
| **A** | **100円** | テーマ × 銀座 | 注目テーマを**銀座で理解する** |
| **B** | **300円** | テーマ × 旬の銀座 × 私だけの銀座時間 | そのテーマを**銀座で体験する**（A の内容＋銀座での過ごし方の商品化） |

- **A と B の差は文字数ではなく価値の階層**（§13.3）。
- ①②別・A/B別の本数配分は固定しない（§16）。
- B（300円）の「私だけの銀座時間」部分は、**将来の GINZA UX体験／
  Concierge の Prototype・需要検証**として扱う。Project 04 との具体的な
  システム接続仕様は**現時点では未確定**（§18）。
- 従来の「② の棲み分けは未決定」という記述は本節（9月Trial 仮説）へ
  更新した。10月本運用前に購入率・満足度・反応を見て見直す（§16・§20）。

### 11.2 「私だけの銀座時間」／300円記事の品質基準（2026-08-31 follow-up・9月Trial 仮説）

**適用範囲**：① 旬の銀座の有料候補「私だけの銀座時間」、および ② の

## 13. Paid Candidate 判定

### 13.1 5軸評価（①②共通）

記事生成後（`reviewStatus=draft` 生成後）、各記事を次の5軸で評価する。
各軸をスコア化し、高評価の記事だけを**有料候補**とする。

| # | 軸 | 見るもの |
|---|---|---|
| 1 | 希少性 | その情報・切り口が他で簡単に手に入らないか |
| 2 | 編集価値 | GINZA WHISKERS の選択・意味づけ・構成がどれだけ効いているか |
| 3 | 実用価値 | 読者の「どう動くか」の判断にどれだけ直結するか |
| 4 | GINZA WHISKERS 固有性 | この編集部でなければ書けない視点・銀座の文脈があるか |
| 5 | 購入意欲 | 読者が「お金を払っても読みたい」と感じる度合い（誇張・煽りで水増ししない） |

- 閾値・配点は運用しながら調整（env 上書き可能な設計余地を残す、§20）。
- **有料候補であっても、最終判断はマロンが行う。**
- **有料価値が弱い場合は無料記事として公開する。**
- 5軸評価は決定的な補助指標であり、9月Trial の
  `interestArticlePostGate` と同じく **WARNING／候補フラグの記録に留め、
  hard gate（自動却下・自動有料化）にしない**。
- 「購入意欲」軸が煽り・クリックベイトを誘発しないよう、Root 憲章
  第2章のトーン原則（上品・記録的・非扇動的）を上位に置く。
- 本判定は記事単位。`PROJECT_02_2_INTEREST_MONETIZATION_SPEC.md` の
  Phase B（paidRatio／monetizationMultiplier）は**テーマ単位**の別レイヤー
  であり、両者は独立して機能する（`GINZA_JOHOKYOKU_SPEC.md` の Paid
  Candidate が下流、Phase B が上流のトピック選定）。

### 13.2 系統ごとの有料候補の作り方

- **① 旬の銀座**：「私だけの銀座時間」型（§11）を有力な有料候補として
  5軸評価する。型は仮説であり固定しない（§11.1）。
- **② 収益化・注目テーマ × 銀座**：9月Trial では5本すべてを原則
  「有料候補」とし、5軸評価（§13.1）で有料価値が成立しないものは無理に
  有料化しない（§9.2、無料公開）。有料化する記事は §13.3 の2層
  （100円／300円）のどちらに該当するかをあわせて判定する。テーマ別に
  「何に対して読者が払うか」（例：情報の網羅性／選定・比較／体験設計／
  背景知識／限定性）を分析し、A（理解）寄りか B（体験）寄りかを提案する
  （分析ロジックは §20 の次工程）。

### 13.3 ② の2層価格モデル（9月Trial 仮説）

② の有料記事は次の2層で扱う。**A と B の差は文字数ではなく価値の階層**。

| | **A：100円** | **B：300円** |
|---|---|---|
| 記事の型 | テーマ × 銀座 | テーマ × 旬の銀座 × 私だけの銀座時間 |
| 読者が得る到達点 | 注目テーマを**銀座で理解する** | そのテーマを**銀座で体験する** |
| 例 | 美容テーマ × 銀座 | 美容テーマ × 旬の銀座 × 散策ルート |
| 内容 | ・注目テーマの整理<br>・銀座での具体例<br>・GINZA WHISKERS の編集視点<br>・なぜ今このテーマなのか<br>・読者が行動判断できる最低限の具体性 | A の内容に加えて：<br>・散策ルート<br>・時間設計・所要時間<br>・店舗／場所の組み合わせ<br>・立ち寄り順（なぜこの順番なのか）<br>・予算感<br>・時間帯<br>・条件別提案<br>・雨天代替<br>——「情報」ではなく「銀座でどう過ごすか」を商品化する |

- **価格（100円／300円）は9月Trial の仮説価格**。本価格として固定
  しない。購入率・満足度・反応を見て**10月本運用前に見直す**（§16・§20）。
- **B（300円）は §11.2 の「300円記事の品質基準」（必須5項目＋原則
  7/10、体験設計型）を満たすこと。** 満たさない場合は B にせず、A
  （100円）または無料へ回す（§11.2.3）。
- B の「私だけの銀座時間」部分は将来の GINZA UX体験／Concierge の
  Prototype・需要検証として扱う（§18、Project 04 接続仕様は未確定）。
- どちらの層も、有料価値が成立しなければ無料公開する（§9.2・§13.2）。

## 14. 有料記事の分類（内部）と価値定義

有料記事は、有料価値の中心によって次の5分類で扱う。**これらは内部の
有料記事分類名**であり、**読者向け本文に内部分類名（「Concierge型」等）を
機械的に表示しない**。読者向けには記事内容に応じた自然なタイトル・
見出しを使う（§4.2・angleSummary と同じ考え方）。

| 分類 | 価値定義 |
|---|---|
| **Concierge** | 読者が「いつ・どこへ・どう動くか」まで決められる |
| **Selection** | 複数候補から GINZA WHISKERS が選び、選定理由まで提示する |
| **Deep Dive** | 背景・文化・歴史・意味まで掘り下げる |
| **Cross Culture** | 海外視点・文化差・訪日視点から銀座を再編集する |
| **Personalization** | 雨の日・ひとり・女性同士・仕事帰り・家族など、条件別に銀座体験を最適化する |

- 有料価値は**文字量ではなく、編集・選択・組み合わせ・行動設計**に置く
  （§9.2・§11 と一貫）。
- 1記事が複数分類の性格を持ってよい。分類は有料候補フラグに添える
  内部の提案情報であり、マロンが取捨する。

### 14.1 当てはめは仮説（9月Trial で検証）

- **5タイプの語彙は内部分類として維持する**が、①②への当てはめ方は
  9月Trial のテーマ別検証による——型を先に固定しない。
- ① 旬の銀座の「私だけの銀座時間」は Concierge / Personalization に近い
  が、Trial で満足度・ボリュームを検証中のため確定させない（§11.1）。
- ② は §13.3 の価格層に対応する目安：**A（100円）＝Selection / Deep Dive
  寄り（テーマを理解する）**、**B（300円）＝Concierge / Personalization 寄り
  （テーマを銀座で体験する）**。ただし当てはめは Trial 検証中で固定しない。
- B（300円）は分類にかかわらず §11.2 の品質基準（体験設計型・必須5＋
  原則7/10）を満たすこと。

## 2. シリーズの趣旨

銀座の新店・イベント・文化・街の変化を毎日収集し、GINZA WHISKERS の
編集視点で「今、知っておきたい銀座＝旬の銀座」を選び、意味づけして
届ける編集メディアとする。

**単なるイベント告知・店舗紹介・公式情報の転載にしない。** すべての
記事に、次の3つを編集価値として必ず加える。

1. **なぜ今なのか**（WHY NOW?）
2. **なぜ GINZA WHISKERS が選ぶのか**（EDITOR'S NOTE）
3. **読者がどう楽しめるのか**（次にどう楽しむか）

この方針は `CLAUDE.md` 第8章「読者接続の編集ロジック」（2026-08-21）・
Editorial Trust Layer 項目4（Fact と Editorial Note の分離）と同一で
あり、本節はそれを日次シリーズの必須要件として明文化したもの。

### 2.1 ① 旬の銀座の役割（funnel・2026-08-31 follow-up）

① 旬の銀座は**基本無料**とし、次の役割を担う。

- 認知拡大
- 読者流入
- GINZA WHISKERS への信頼形成
- 今日知る価値のある銀座情報の提供

新店・イベント・文化・店舗・体験・街の変化を、単なる告知転載ではなく
GINZA WHISKERS の編集視点で届ける（§10）。② の有料記事は、この信頼の
上に成り立つ。

## 3. 記事冒頭の基本表現（マストヘッド）

### 3.1 基本形

```
銀座情報局 by GINZA WHISKERS
旬の銀座を、毎日。

銀座の新店、イベント、文化、街の変化から、
今だから知っておきたい銀座を
GINZA WHISKERS の編集視点で届けます。
```

### 3.2 運用ルール

- **1〜2行目（シリーズ名＋コアフレーズ）は毎記事に置く。**
- **3行目以降の説明文は、記事のボリューム・内容に応じて短縮・省略して
  よい。** 短文記事では1〜2行目のみ、または説明文を1文に圧縮する。
- Editorial Style Engine 項目2「長い挨拶から始めない」と両立させる
  ——マストヘッドは定型の看板であって挨拶ではない。マストヘッド直後の
  本文は、季節感・街の空気・今週性を短く述べてから本題に入る。
- 毎記事で同じ長い説明文を機械的に繰り返さない。

## 4. 記事基本構成（日次・単一トピック）

原則として以下を基本骨格とする。

| # | ブロック | 内容 |
|---|---|---|
| 1 | 銀座情報局 by GINZA WHISKERS（マストヘッド） | §3 |
| 2 | 旬の銀座（導入） | 今なぜこの銀座か。季節・街の空気・今週性を短く |
| 3 | **WHY NOW?** | なぜ今、この情報なのか（確認済みの会期・季節文脈に接地） |
| 4 | **EDITOR'S NOTE** | なぜ GINZA WHISKERS が選んだのか（Fact と分離） |
| 5 | 出典 | §7 の読者向け整形形 |
| 6 | 次にどう楽しむか | 読者の行動・体験につながる短い導線（1文・1アクション＝既存 `callToAction`） |

### 4.1 短文記事での省略

短文記事では、すべての見出しを強制しない。内容に応じて自然に統合・
省略してよい（例：WHY NOW? と EDITOR'S NOTE を1段落に統合、導入と
マストヘッド説明文をまとめる）。

### 4.2 内部情報を読者向け本文に出さない（angleSummary）

`angleSummary`（`generateMultiAngleArticleDrafts.ts`）は、生成制御・
内部編集用のフレーミング情報として扱い、**読者向け note 本文の見出し
として表示しない**。現在の `buildAngleArticleBlocks` は `angleSummary`
を h2 見出しへ出力しており、記事の主見出しとして不自然なメタ文
（例：「…を GINZA WHISKERS の編集視点で紹介する記事」）になる事例が
ある（Trial #53）。これは、生成用・内部用の文言がそのまま読者向け
本文に出てしまう問題であり、§7.1 の `[IMAGE:]` マーカーと同じ考え方で
防止する。マストヘッド（§3）・WHY NOW? / EDITOR'S NOTE を骨格の見出し
とする。

## 7. 内部マーカー・出典表記の読者向け整形

### 7.1 内部画像マーカー

`[IMAGE: アイキャッチ]` `[IMAGE: 見出し …]` などの内部制御表記は、
**note 転記用本文・公開本文に絶対に残さない。**

- 実画像を挿入できる場合 → 実画像へ置換
- 実画像がない場合 → **自動削除**（マーカー行を本文に残さない）
- 画像の配置意図は本文テキストではなく、パッケージのメタ情報
  （`note-draft.json` の `images[].placement` 等）で保持する

### 7.2 出典表記

内部ログ形式（`SOURCE: <名称>／確認: <日付>／<URL>`）を読者向け本文に
そのまま出さない。note 公開用は自然な表記へ整形する。

```
出典：銀座 蔦屋書店
公式情報を確認：2026-08-31
```

必要に応じて公式 URL をリンクとして付与する。`CLAUDE.md` 第8章
Editorial Style Engine 項目10 の読者向け表示形は本節の表記で更新する
（実装は §20）。

# 無料／有料コンテンツ設計

## 9. 基本原則

### 9.1 対象の2系統と無料／有料の考え方の違い（2026-08-31 follow-up・確定）

無料／有料化の考え方は **① 旬の銀座 と ② 売れるテーマ × 銀座 で
同一にしない**（適用範囲の表を参照）。

| | ① 旬の銀座（5本） | ② 売れるテーマ × 銀座（5本） |
|---|---|---|
| **無料記事** | 銀座のイベント・新店・文化・店舗・体験の**コンテンツ情報紹介**を基本とする（§10） | 9月Trial では原則置かない（5本すべて有料候補）。有料価値が成立しない記事のみ無料公開（§9.3） |
| **有料候補** | **「私だけの銀座時間」**（読者の銀座体験そのものを設計する）を**有力な有料候補として検証する**（§11、9月Trial） | **9月Trial 仮説：5本すべて原則「有料候補」。2層価格（A=100円 テーマ×銀座＝「理解」／B=300円 テーマ×旬の銀座×私だけの銀座時間＝「体験」）**（§9.3・§13.3） |

- ① の有料候補「私だけの銀座時間」は、**将来の GINZA UX体験（Root
  `CLAUDE.md` 第1章の Project 04、現在"未確認"）につながる Trial** として
  扱う。ここで cross-project の仕様を先取りしては作らない。
- ① について「旬の銀座の有料記事＝必ず散策ルート」とは**まだ固定しない**
  （§11）。
- ② の無料／有料は「未決定」から **9月Trial の2層価格仮説（100円／300円）**
  へ更新した（§9.3）。価格は本価格として固定せず、10月本運用前に見直す。
- ② B（300円）の「私だけの銀座時間」部分は将来の GINZA UX体験／Concierge
  の Prototype・需要検証（§18、Project 04 接続仕様は未確定）。

### 9.2 両系統に共通する原則

- 無料記事と有料記事の差は、**「文字数」や「情報量」ではなく、読者が
  得られる編集価値・判断価値・行動価値で作る**。
- **無料記事を意図的に薄くして、続きを有料に誘導する設計は禁止する**
  （Root 憲章第2章「非扇動的」・Editorial Trust Layer を適用）。
- **無料記事単体でも「読んでよかった」「今の銀座が分かった」という満足
  が成立することを必須とする。**
- 有料記事は、無料記事では得られない追加価値（選択・比較・組み合わせ・
  ルート設計・時間短縮・条件別最適化など。具体は系統ごとに §11・§13.2〜
  §13.3）を提供する。**有料価値が成立しない記事を、本数合わせのために
  有料化してはいけない**（§16.1）。
- 記事生成後の Paid Candidate 5軸評価（§13.1）と、**最終的な無料／有料
  判断はマロン**が行うことは、①②とも共通。

### 9.3 ② の無料／有料の棲み分け（2026-08-31 follow-up・9月Trial 仮説）

## 11. 「私だけの銀座時間」（300円記事・9月Trial 検証・仮説）

「私だけの銀座時間」は、100円記事の単純な長文化ではない。

  テーマ／旬の銀座 × ターゲットの気分・目的 × 体験ルート

まで編集した **体験設計型コンテンツ**とする。基本価値は「**この通りに
動けば、自分らしい銀座時間を過ごせそう**」と読者が感じられること
（§11.2.5）。位置づけは将来の GINZA UX体験／Concierge の Prototype・
需要検証（§18）。**毎日必ず作る商品ではなく、十分な付加価値を作れる
テーマだけを選抜**して300円候補とする（§16.3）。

**適用範囲**：① 旬の銀座の有料候補、および ② の B＝300円（§13.3）。
② B は本節の設計要素をテーマ文脈で応用する。

以下のうち複数を編集して提示する。

- 散策ルート
- 時間設計・所要時間
- 立ち寄り順（なぜこの順番なのか）
- 組み合わせ（何と合わせるか）
- 予算感
- 時間帯別の楽しみ方
- 対象読者（誰に向くか）
- 雨天代替
- 各地点での体験ポイント
- どれを選ぶべきか・比較
- 編集者による判断

**単なる情報追加や長文化だけでは有料化しない。**

### 11.1 仮説であること・未確定事項

- 「私だけの銀座時間」は**有力な有料候補であって確定ではない**。
  **「旬の銀座の有料記事＝必ず散策ルート」とはまだ固定しない。**
- 有料記事としてどこまで情報・体験設計を提示すれば十分な満足度になるかは
  **未確定**。9月Trial で内容・ボリューム・満足度を検証する。
- 「私だけの銀座時間」は将来の GINZA UX体験（Project 04、"未確認"）へ
  つながる Trial として扱う（§9.1）。
- ① の「私だけの銀座時間」の価格は**未決**（② は100円が基本商品・B が
  300円と確定したが、① 単体の価格帯は定めていない。§20）。

### 11.2 「私だけの銀座時間」／300円記事の品質基準（2026-08-31 follow-up・9月Trial 仮説）

### 11.3 Primary Persona（主ターゲット・2026-08-31 follow-up）

「私だけの銀座時間」の **Primary Persona（主ターゲット）** は、**銀座が
似合う、少し背伸びしたくなる20代後半〜30代女性**。

想定：仕事を持つ／銀座の常連とは限らない／感度は比較的高い／一人
または友人と行動／かわいいだけでなく上質さを求める／自分へのご褒美
や自分を整える時間に価値を感じる／新しい銀座を知りたい／普段より
少しだけ背伸びした体験をしたい。

- これは **Primary Persona であって、対象をこの層だけに限定する仕様に
  はしない**。将来的な別世代・訪日女性等への展開余地を残す。
- Project 02「私だけの銀座時間」の編集判断用であり、ブランド全体の
  ターゲット定義ではない。

### 11.4 Editorial Compass（編集指針・2026-08-31 follow-up）

「私だけの銀座時間」の企画・店選び・ルート・文章トーンの判断指針
（**Editorial Compass**）として、次の要素バランスを用いる。

| 要素 | 目安 |
|---|---|
| かわいい | 20 |
| 上質 | 30 |
| 自分を整える | 25 |
| 新しい発見 | 15 |
| 少し背伸び | 10 |

- **数値による機械的な合否判定には使わない。** 各体験が GINZA WHISKERS
  らしい世界観になっているかを判断するための編集指針として扱う。
- **テーマ・季節・気分によって各要素の強弱は変動してよい。** ただし
  全体として **「上質」「自分を整える」を中核価値**とする。
- 「かわいい」「スイーツ」「映え」を、女性向けだからという理由だけで
  機械的に入れない。
- スイーツ・コスメ・香り・アート・書店・ホテル・カフェ・夜景・街歩き・
  文化等は、その日の体験テーマに必要な場合のみ組み込む。

### 11.5 気分・目的からの体験設計

「私だけの銀座時間」は、店ジャンルからスタートするだけでなく、
**「今日はどんな自分でいたいか」**から設計できるようにする。

例：仕事帰りに自分を整えたい／一人で静かに過ごしたい／少し贅沢したい
／新しいものに出会いたい／雨の日でも銀座を楽しみたい／疲れた金曜日に
自分へご褒美／少し背伸びした夜。

編集順：**気分・目的 → 旬の銀座 → 体験の組み合わせ → ルート**。
（`CLAUDE.md` 第8章「読者接続の編集ロジック」の「私だけの銀座時間」
向け具体化。）

### 11.6 実地調査の扱い（編集提案型ルート・2026-08-31 follow-up・確定）

- Project 02 の収益化記事では、**マロンの事前実歩を公開前の必須条件に
  しない**（旬の情報を当日中に届ける即時性を優先）。
- 「私だけの銀座時間」および ② の記事は、**公式情報・営業時間・位置
  関係・移動時間・予約要否・予算**等を確認した「**編集提案型ルート**」
  として提示する（各事実は Editorial Trust Layer の Source Provenance
  対象）。
- **実歩していない場合、実地検証済みと誤認させる表現を禁止する**
  （「歩いてきました」「実際に回った」等を使わない。Editorial Trust
  Layer 準拠）。
- マロンの実歩・現地検証は、**将来の GINZA UX体験／アプリ側で体験品質
  を高度化するために活用**する（Project 02 の公開ゲートには使わない）。

## 13. Paid Candidate 判定

### 13.1 5軸評価（①②共通）

記事生成後（`reviewStatus=draft` 生成後）、各記事を次の5軸で評価する。

| # | 軸 | 見るもの |

## 14. 有料記事の分類（内部）と価値定義

有料記事は、有料価値の中心によって次の5分類で扱う。**これらは内部の
有料記事分類名**であり、**読者向け本文に内部分類名（「Concierge型」等）を
機械的に表示しない**。読者向けには記事内容に応じた自然なタイトル・
見出しを使う（§4.2・angleSummary と同じ考え方）。

| 分類 | 価値定義 |
|---|---|
| **Concierge** | 読者が「いつ・どこへ・どう動くか」まで決められる |
| **Selection** | 複数候補から GINZA WHISKERS が選び、選定理由まで提示する |
| **Deep Dive** | 背景・文化・歴史・意味まで掘り下げる |
| **Cross Culture** | 海外視点・文化差・訪日視点から銀座を再編集する |
| **Personalization** | 雨の日・ひとり・女性同士・仕事帰り・家族など、条件別に銀座体験を最適化する |

- 有料価値は**文字量ではなく、編集・選択・組み合わせ・行動設計**に置く
  （§9.2・§11 と一貫）。
- 1記事が複数分類の性格を持ってよい。分類は有料候補フラグに添える
  内部の提案情報であり、マロンが取捨する。

## 16. 初期運用目安（Trial 仮説値）

### 16.1 ①② 合算

1日10本（① 5本＋② 5本。10月からの戦略的な最低運用基準・§8.3・§8.6）。
**有料記事数をノルマ化しない**——その日に有料価値のある記事がなければ、
10本すべて無料でもよい（本数基準は「投稿数」の話で、「有料本数」の
ノルマではない）。**有料価値が成立しない記事を、本数合わせのために
有料化してはいけない**（§9.2）。最終的な無料／有料判断はマロン。

### 16.2 ① 旬の銀座（5本）

無料記事を基本とし、有料候補として「私だけの銀座時間」（§11）を Trial
する。①内の無料／有料本数は固定しない。

### 16.3 ② 売れるテーマ × 銀座（5本）

- **5本は原則100円有料記事（基本商品）**。有料価値が成立しないものは
  無料公開（§9.2）。
- **300円（B）は選抜制**——§11.2 の品質基準＋§11.2.5（意思決定負荷）を
  満たすテーマだけ。**毎日必ず作らない**。初期Trial 例：300円は 0〜2本
  ／日（A/B の配分は固定せず、日ごとのテーマ価値と §11.2 基準の充足で
  決まる）。
- テーマは「売れるテーマ候補プール」から時期の強さで選ぶ（初期候補
  AI／働き方／美容／人間関係／お金／学び。例示であって限定しない。
  `PROJECT_02_2_INTEREST_MONETIZATION_SPEC.md` §1.1）。

### 16.4 価格・品質基準の見直し

100円／300円は9月Trial の仮説価格、§11.2 の「必須5＋原則7/10」「地点数
3〜5」・§11.4 の Editorial Compass 配分値は9月Trial の仮説基準。いずれも
本運用の固定値としない。購入率・読者反応・満足度・編集提案型ルートと
しての成立性（§11.6）・意思決定負荷の低減（§11.2.5）を見て
**10月本運用前に見直す**（§9.3・§11.2.4・§16.5・§20）。

### 16.5 9月Trial で検証すること

1. 売れるテーマ候補の抽出精度
2. 100円記事の購入率
3. どのテーマが購入されやすいか
4. 300円化すべきテーマの条件
5. 「私だけの銀座時間」の満足度
6. Primary Persona（20代後半〜30代女性）に刺さる気分・目的
7. 100円と300円の価値差が明確か
8. 300円記事の最適頻度
9. 価格 100円／300円の妥当性

100円／300円は Trial 仮説価格。10月本運用前に見直す（§16.4）。

### 16.6 第一KPI（10月末）と月次検証（2026-08-31 follow-up）

**10月末の第一KPI**：売上額だけでなく、**有料で購入される「テーマ ×
記事型 × 価格」の勝ちパターンを 3〜5型発見する**こと。

- **価格も検証単位に含める**（最上位目的が「売れるテーマ・価格・記事型
  の最短発見」であるため）。テーマ・記事型が同じでも価格が違えば別
  パターンとして扱う。
  - 例：美容 × 100円 Insight型／美容 × 300円 私だけの銀座時間／
    AI × 100円 Insight型 ——これらを別々の検証パターンとする。
- **100円／300円は9月Trial〜10月時点の仮説価格であり、固定価格では
  ない**（§16.4）。
- 11月：発見した勝ちパターンへ ①②・A/B・テーマの配分を寄せる。
- 12月：勝ちパターンの再現性（別テーマ・別週でも成立するか）を検証する。
- 検証データは §16.5 の9項目＋§17 の学習メタで蓄積する。

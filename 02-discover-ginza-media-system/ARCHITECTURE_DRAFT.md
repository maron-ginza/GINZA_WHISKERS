# Discover GINZA Media System — MVPアーキテクチャ設計（ドラフト）

**ステータス：承認済み（2026-07-21）。確定事項は `CLAUDE.md` 第8章・
第12章に反映済み。本ファイル自体はCLAUDE.mdの「更新の粒度」原則
（第7章）により肥大化を避けるため、実装タスクの逐次進捗はここではなく
別途タスク管理（Issue等）で追跡する。**

**前提となる合意事項（本セッション）**：
- 記事生成におけるAIの人間関与レベル＝「AI下書き＋人間が編集長として
  全面レビュー」。第8章のAI活用ポリシー（AI支援・人間承認、自動投稿なし）
  を記事生成にも同様の考え方で拡張する。この拡張は本ドラフト承認時に
  第8章へ反映する。

**このドラフトが決めないこと**：具体的なCMS・ホスティング・フレームワーク
選定（第6章：技術選定はデザイン確定後）、ビジュアルデザイン（第5章）、
翻訳ワークフロー（第7章）。これらは必要要件として記述するが、製品選定は
別セッションに委ねる。

## 1. 全体像：AI編集部のパイプライン

```
[情報収集]
    │  （収集された素材・ソース・ネタ）
    ▼
[記事生成：AI下書き]──┐   （本文＋SEOメタ＋チャネル別ソーシャルコピー案を同時生成）
    │                  │（画像が必要な場合）
    ▼                  ▼
[編集長レビュー] ◀── [画像管理：候補提示]
    │  （人間が全面レビュー・修正・確定）
    ▼
[承認キュー]
    │  （承認＝正式コンテンツとして確定）
    ▼
[Content Asset Repository]
    │  （構造化コンテンツの単一の保管庫。以降すべてのチャネルはここから読む）
    ▼
 分岐 ──┬─────────────┬─────────────┬─────────────────┬───────────┐
        │             │             │                 │           │
        ▼             ▼             ▼                 ▼           ▼
   [02サイト公開]  [noteパッケージ [X投稿：      [Instagram投稿： [ニュースレター
    （記事＋         生成]         承認済み       承認済み          配信]
     ギャラリー）      │           コピーをAPI送信] コピーをAPI送信]
                       ▼
                 [人間が手動投稿]
                 （note公式APIなし）
```

**設計原則（憲章から継承）**：
- すべての配信チャネルで「AIが案を作り、人間が承認してから外部に出る」
  ゲートを共通化する。承認キューは記事・SNS共通の1つの管理画面とする
  （チャネルごとに別々の承認UIを作らない）。
- 承認前のコンテンツは一切外部に公開・送信されない。
- **Create Once, Publish Everywhere**：承認されたコンテンツはチャネルごとに
  作り直すのではなく、Content Asset Repositoryに一度だけ構造化保存し、
  各チャネルはそこから必要な形に変換して取り出す（詳細は2.4節）。

## 2. コンポーネント別設計

### 2.1 情報収集（Research Intake）

**MVPスコープ**：まずは人間が収集したネタ・素材を投入する「受け皿」を
作ることを優先する。全自動のクローリングはPhase 3（将来の自動化）に回す。

- 入力形式：URL・テキストメモ・画像・PDF等を1件の「ソース」として登録
- 各ソースに6本柱（歴史・文化・アート・建築・人物・イベント）のタグ付け
- ソースの状態管理：未着手／記事化中／記事化済み
- 検討事項（要決定・将来）：Ginza関連ニュースのRSS監視、Web検索エージェント
  による自動ネタ出し。事実確認の難易度が上がるため、Phase 1では見送る。

### 2.2 記事生成（AI下書き → 編集長レビュー）

- ソース（複数可）を選択 → AIが構成案＋本文下書きを生成
- 下書きは6本柱タグ・トーン原則（上品・記録的・非扇動的）を踏まえた
  プロンプト設計とする
- 編集長レビュー画面で全文修正可能（差分ではなく編集画面での直接編集を想定）
- 状態遷移：`draft(AI生成)` → `review(編集中)` → `approved(承認)` →
  `published(公開)`
- バイリンガル対応：コンテンツモデルは日本語・英語を1記事内の別フィールド
  として持つ設計とする。翻訳をAI支援にするか人力にするかは第7章の未決事項
  のため、翻訳ステップは「差し替え可能な工程」として設計上分離しておく
  （決定後に実装を差し込めるようにする）。

### 2.3 画像管理

- 単一のアセットライブラリとして構築し、01（ブランドサイト）とは独立した
  ストレージを持つ（02は独自サブブランドのビジュアルのため）
- 必須メタデータ：出典・権利関係（archival photoは著作権・使用許諾の確認が
  必須）、6本柱タグ、代替テキスト（アクセシビリティ／多言語）
- チャネル別書き出し：ギャラリー用オリジナル解像度、Instagram用正方形/
  縦長クロップ、X用横長クロップ、note用ヘッダー画像、を1枚の元画像から
  自動生成する変換パイプラインを持つ（手動クロップ地獄を避ける）

### 2.4 Content Asset Repository（構造化コンテンツの単一の保管庫）

承認されたすべての記事は、公開先ごとに別々のフォーマットで持つのではなく、
**再利用可能な構造化コンテンツ**として1箇所に保存する。note・X・
Instagram・ニュースレター・将来のブランドサイト連携など、どのチャネルも
この保管庫を読みに来る「ハブ」として設計する（＝Create Once, Publish
Everywhere。個々のチャネル用出力は保管庫からの変換結果であり、それぞれの
チャネルで独自に本文を作り直さない）。

**保有するフィールド（最低限）**：
- `title`：日本語／英語（別フィールド、翻訳ステータスと紐づく）
- `body`：本文（構造化ブロック。見出し・引用・画像埋め込み位置を保持し、
  チャネルごとの整形を機械的に行えるようにする）
- `images`：画像管理（2.3節）内アセットへの参照。ギャラリー用原寸・
  チャネル別クロップ済みバリアントを含む
- `tags`：6本柱タグ＋自由タグ
- `seo_metadata`：メタタイトル・メタディスクリプション・スラッグ・
  OGP画像参照
- `social_copy`：note／X／Instagram向けのキャプション案（チャネルごとの
  文字数制約・トーンに合わせた別バリアント。記事生成時にAIが本文と同時
  生成し、編集長レビューの対象に含める）
- `translation_status`：フィールド単位（title/body等）での翻訳状態
  （未翻訳／翻訳中／翻訳済み）。ワークフロー自体は第7章の未決事項のため、
  ステータスの置き場所だけを今のうちに確保する
- `publish_history`：チャネルごとの配信状況（配信済み／未配信・配信日時）。
  同じ記事を後日別チャネルへ再利用・再配信する際に、二重配信や配信漏れを
  防ぐために必要

**設計上のポイント**：
- 各チャネルの配信処理（noteパッケージ生成、X投稿、Instagram投稿、
  ニュースレター編纂、将来の02サイト以外への露出）は、すべてこの保管庫を
  読み取り専用ソースとして参照する。チャネル側のロジックが記事の正本を
  書き換えることはない。
- 02サイトの記事ページ自体も、この保管庫からのレンダリング結果として
  扱う（サイト表示とSNS配信を別データソースにしない）。

### 2.5 承認キュー（人間ゲート・共通コンポーネント）

- 記事・note・X・Instagramの下書きが一覧化される単一ダッシュボード
- 各項目に「承認して配信」「差し戻し」「破棄」のアクション
- 承認ログを残す（誰が・いつ承認したか。ブランドの信頼性担保のため）
- 承認操作の完了がContent Asset Repositoryへの確定保存のトリガーとなる

### 2.6 配信：note / X / Instagram

**note投稿**
- **制約**：note.comに公式パブリック投稿APIは存在しない。非公式手段は
  規約違反・仕様変更で壊れるリスクがあるため、MVPでは採用しない。
- 設計：AIが本文（note向けフォーマット）＋画像を「コピー＆ペースト
  可能なパッケージ」として生成 → 編集長が承認 → 人間がnote管理画面で
  手動投稿。将来note側が公式APIを提供した場合のみPhase 3で自動化を再検討。

**X投稿**
- X API v2（OAuth 2.0）で投稿自体は技術的に可能。無料枠でも投稿数上限
  付きで書き込み可能（枠・料金体系は変動するため、実装直前に最新の
  API利用条件を確認する）。
- 設計：AIが下書き生成 → 承認キューで人間承認 → 承認と同時にAPI経由で
  投稿（＝「自動投稿」ではなく「人間承認後の自動送信」。第8章の
  「自動投稿は行わない」＝人間の確認を経ない配信をしない、の原則には
  抵触しない）。

**Instagram投稿**
- Instagram Graph API（Content Publishing API）が必要。前提条件：
  Instagramビジネス/クリエイターアカウント、Facebookページとの連携、
  Meta社によるアプリ審査（本番運用には数週間单位のリードタイムが
  発生しうる）。画像は公開URLからの取得が必要（直接アップロード不可）。
- 設計：X同様、承認後にAPI経由で投稿。ただし**Meta審査のリードタイムを
  踏まえ、Instagram連携は着手を早めに開始する**必要がある（Phase 2の
  中でも最初に着手すべき項目として扱う）。

## 3. 技術的制約まとめ（実装前に必ず確認）

| チャネル | 自動投稿の技術的可否 | 主な制約 |
|---|---|---|
| note | 不可（公式APIなし） | 人間による手動投稿が前提。将来API公開時に再評価 |
| X | 可（承認ゲート付き） | API利用枠・料金体系を実装直前に要確認 |
| Instagram | 可（承認ゲート付き） | ビジネスアカウント化＋Meta審査が必要。リードタイム考慮 |

## 4. MVPフェーズ計画（開発タスク分解）

憲章第3章の合意（記事＋ギャラリー先行、ニュースレター・SNSは後続）に
準拠したフェーズ順序。

### Phase 0：前提決定（本ドラフトのレビューと並行して進める）
- [ ] ビジュアルデザイン確定（第5章：デザイン確認セッション）
- [ ] 技術選定確定（第6章：CMS/ホスティング/フレームワーク）
- [x] 本ドラフトの承認 → CLAUDE.md第8章・第12章への反映（2026-07-21完了）

### Phase 1：記事＋ギャラリー基盤（コアコンテンツ基盤）
- [ ] コンテンツモデル設計（記事・画像・ソース・タグのスキーマ、
      draft/review/approved/publishedの状態遷移）
- [ ] **Content Asset Repositoryの構築**（title/body/images/tags/
      seo_metadata/social_copy/translation_status/publish_historyを
      持つ構造化スキーマ。02サイト・SNS・ニュースレター共通の正本とする）
- [ ] 画像管理基盤（アセットライブラリ＋権利メタデータ＋チャネル別書き出し）
- [ ] 情報収集の受け皿（ソース登録・タグ付けのシンプルなUI）
- [ ] AI記事生成パイプライン（本文に加え、SEOメタ・チャネル別ソーシャル
      コピー案を同時生成。プロンプト設計は6本柱＋トーン原則を埋め込む）
- [ ] 編集長レビューUI（本文・ソーシャルコピー案を一括で全文編集・承認）
- [ ] 02サイトへの公開パイプライン（Content Asset Repositoryからの
      レンダリングとして実装。記事＋ギャラリー表示）
- [ ] バイリンガルのデータモデル対応（翻訳工程は差し替え可能な形で分離、
      translation_statusで進捗管理）

### Phase 2：AI支援SNS配信（承認ゲート付き自動送信）
- [ ] 共通承認キューダッシュボード（記事・SNS横断）
- [ ] note配信パッケージ生成（Content Asset Repositoryのsocial_copy/
      imagesから、コピペ用フォーマットを生成。手動投稿前提）
- [ ] Instagram連携（ビジネスアカウント化・Meta審査を最優先で着手。
      承認済みsocial_copyをAPI送信）
- [ ] X API連携（OAuth設定・投稿API・承認済みsocial_copyを自動送信）
- [ ] ニュースレター配信（Content Asset Repositoryから複数記事を編纂。
      憲章第3章：SNSと同フェーズ内で後続として着手）

### Phase 3：将来の自動化（コミットしない拡張ロードマップ）
- [ ] 情報収集の自動化拡張（RSS監視・Web検索エージェントによるネタ出し）
- [ ] 承認ワークフローの効率化（バッチ承認・配信スケジューリング）
- [ ] note公式API公開時の自動投稿統合（条件付き・現時点では前提にしない）
- [ ] 完全自動投稿（人間承認なし）への移行可否の再評価
      → **これは第8章の原則そのものの見直しを意味するため、デフォルトの
      方向性としない。将来検討する場合は独立した意思決定として扱う。**

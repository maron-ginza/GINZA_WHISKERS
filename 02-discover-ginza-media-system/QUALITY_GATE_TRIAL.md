## 1. 会場判定ロジックの改善案

### 1.1 発見された問題の分析

`NOTE_ARTICLE_TRIAL.md`執筆時、パク・ヨンジェ個展「回帰線：永遠が留まる場所」について、
Editor's Choice Trial段階では「GINZA SIXと銀座 蔦屋書店の双方で開催」という前提で
クロスサイト重複を統合していた。しかし執筆段階で両ソースの本文を実際に確認したところ、
**実際の開催会場は銀座 蔦屋書店内「FOAM CONTEMPORARY」1箇所のみ**で、GINZA SIX側の
記事はそれを紹介する告知記事（二次告知）だと判明した。

原因は、「掲載サイトのドメイン＝開催会場」という暗黙の前提を置いていたこと。
GINZA SIXのニュースページに掲載されている＝GINZA SIXで開催、という短絡的な
対応付けが、今回のようなクロスプロモーション（近隣施設同士の相互紹介）の実例では
誤りになる。

### 1.2 用語の整理（区別すべき6概念）

| 概念 | 定義 | 今回の実例 |
|---|---|---|
| **実開催会場** | イベントが物理的に行われる場所 | 銀座 蔦屋書店内「FOAM CONTEMPORARY」 |
| **主催者** | イベントを企画・運営する主体（会場運営者と同一とは限らない） | 今回は未確認（ギャラリー運営者名は本文になし） |
| **二次告知サイト** | 実開催会場ではないが、そのイベントを紹介・宣伝しているサイト | GINZA SIXニュースページ（回帰線の記事） |
| **商業施設内テナント** | 実開催会場が商業施設内の特定店舗・ギャラリーである場合 | 「銀座 蔦屋書店」という施設名と「FOAM CONTEMPORARY」というテナント（ギャラリー）名は別物として扱う |
| **クロスサイト告知** | 同一イベントが複数サイトで紹介されている現象そのもの（それ自体は複数会場開催を意味しない） | 回帰線が2サイトに掲載されていたこと自体 |
| **同一イベントの別会場開催** | 本当に複数の物理的場所で同時開催されるケース | フジサキタクマ「MOLnarrative」（GINZA SIX本会場＋銀座 蔦屋書店内GINZA ART SQUARE＋スターバックス前、の3箇所でのサテライト展示。excerptで実際に確認済みの実例） |

**「回帰線」と「MOLnarrative」の違いに注意**：前者は同一イベントの二次告知（会場は1箇所）、
後者は本当に複数箇所で関連展示を行う設計（本会場＋サテライト）——表面上は似た
「複数サイト掲載」でも、実態は異なる。これが今回の誤認の核心である。

### 1.3 判定ルール案

```
IF 複数サイトに同一タイトル・同一会期の記事が存在する THEN
  各ページ本文から「会場記述」（「〜にて開催」「会場：」「店内〇〇にて」等の
  ラベル付き表現）を抽出する。

  IF 全ページが同一の具体的会場名（テナント名まで一致）を明示している THEN
    → 実開催会場＝その1箇所。会場名を明示しなかった／曖昧な表現
      （「当施設」「店内」等、テナント名の記載がない）のページは
      「二次告知サイト」として扱う。

  ELSE IF 一部ページのみ具体的な会場名（テナント名）を持ち、他は会場名の
          記述自体がない THEN
    → 会場名を持つページを一次情報として優先する。会場名がないページは
      二次告知として扱い、統合時の主表示には使わない（ただし情報源としては
      両方保持する）。

  ELSE IF 明確に異なる複数の会場名が本文に記述されている THEN
    → 「同一イベントの別会場開催」の可能性を検討する。両方の会場を
      本文に明記し、統合して1会場に単純化しない（両論併記）。

  ELSE（会場記述が曖昧・矛盾しており解決できない） THEN
    → 「会場未確認」とする。推測で会場を確定させない。
END IF

原則：「掲載サイトのドメイン／施設名＝開催会場」と自動的に判断しない。
掲載元サイトの運営者名と、本文中の会場表記が一致するかを個別に確認する。
```

### 1.4 一次情報の優先順位（推測しない原則の適用）

1. イベント本文中に明示的な会場ラベル（「会場：」「〜にて開催」等）があるページ
2. JSON-LD構造化データの`location`（`extractStructuredDates.ts`が既に抽出しているvenueフィールド、Tier 1相当）
3. 上記いずれもない場合は「会場未確認」とし、掲載サイト名から推測しない

## 2. Fact / Editorial の分離

記事内の情報を3種類に分類し、混同しないルールを定める。

| 分類 | 定義 | 表記ルール |
|---|---|---|
| **A. Confirmed Fact** | 一次情報または信頼できる公式情報（SOURCE LEDGER上のexcerpt本文）で確認済みの事実 | 本文の事実記述部分。情報源URLと対応づけ可能であること |
| **B. Unconfirmed** | 情報源上で確認できない項目 | 本文の主要な訴求（タイトル・冒頭リード・見出し）には使わない。使う場合は「（未確認）」等を明示するか、別表に切り出す |
| **C. Editorial Note** | GINZA WHISKERSによる編集コメント・解釈・推薦 | 独立した見出し（「Editor's Note：」等）配下に必ず置く。事実文の末尾に断定的な編集評価を継ぎ足す書き方は禁止 |

**混同防止ルール**：
- 1つの文中でFactとEditorial Noteを混在させない（例：「〜な展覧会で、きっと心に残るはずです」のように事実描写と主観評価を同一文に混ぜない）
- Unconfirmedな情報は記事の主要な訴求に使わない
- `NOTE_ARTICLE_TRIAL.md`は既にこの形式（各候補の本文記述とEditor's Noteを見出しで分離）に準拠していたことを確認済み

## 4. Quality Gate仕様

### 4.1 判定区分

**BLOCKER**（掲載不可、公開前に必ず解消）

| 条件 | 理由 |
|---|---|
| 開催日／開催期間が不明 | ongoing/upcoming/endedの判定自体ができない |
| 会場が不明、または会場記述に矛盾があり未解決 | 読者が実際に行けない。**今回の「回帰線」誤認がまさにこれに該当**（詳細は§5） |
| イベントが終了済み（`deriveEventStatus`＝ended）と判明している | 読者を無駄足にさせる |
| 情報源間で事実が矛盾しており解決していない（会場以外：会期・料金等） | 誤情報の掲載リスク |
| 同一イベントの重複が統合・両論併記いずれの処理もされていない | 同じイベントが複数枠を占有し、他の候補を圧迫する |
| Content Richness＝boilerplateで、掲載する例外理由が記録されていない | 記事化に足る材料がない |

**WARNING**（掲載可、ただし公開前に人間の確認を推奨）

| 条件 | 理由 |
|---|---|
| 料金未確認 | 実用情報として重要度が高いUX Typeでは特に注意 |
| 予約要否未確認 | 同上 |
| 所要時間未確認 | 同上（体験系で特に重要） |
| 営業・開催時間未確認 | 参考情報 |
| アクセス情報未確認 | 参考情報 |
| 写真撮影可否未確認 | 展覧会系で重要度が高い |
| Content Richness＝thin | boilerplateほどではないが情報が薄い |

**PASS**：上記いずれにも該当しない

**画像が外部画像しか存在しないこと自体はBLOCKER/WARNINGのいずれにもしない**
（2026-08-19、Editorial Trust Layer確定・`CLAUDE.md`第8章、`IMAGE_USAGE_TRIAL.md`
参照）——旧版では「画像未選定」をWARNINGとしていたが、Editorial Trust Layer確定
により「外部画像は原則転載しない、独自画像または画像なしで対応する」という
正式方針が定まったため、画像の有無はGate判定から独立した別軸として扱うことに
改めた（本ファイル初版からの修正点）。

### 4.2 ユーザー提示例からの修正点

- 「同一イベント重複」は単純なBLOCKERにせず、**「重複が未処理のまま」**という条件に修正した——今回のように統合・両論併記のいずれかで処理済みであれば、重複の存在自体はBLOCKERにならない
- 「会場不明」に加え、**「会場記述の矛盾が未解決」**を明示的にBLOCKERへ追加した——今回発見した問題はまさにこのケース（会場が「不明」だったのではなく「複数サイトの記述をどう解釈するか」が未解決だった）
- （2026-08-19追記）「画像未選定」をWARNINGから削除した——Editorial Trust Layer確定により画像はGate判定と独立した別軸になったため

### 6.2 著作権・利用条件についての原則

**og:image／twitter:imageの取得は、あくまでページ表示（プレビュー用）を目的とした
埋め込みであり、SNS・note記事での二次利用や商用転載の許諾を意味しない。**
利用可否が個別に確認できない場合、「使ってよい」とは推測しない——既定は
「転用不可」として扱い、実際にnote/SNSで使用する前に、各サイトの利用規約確認・
掲載元への許諾確認を必要とする。

## 7. 最終報告

### ① 今回発見した品質問題

**会場誤認**（パク・ヨンジェ個展「回帰線」）——「掲載サイト＝開催会場」という
暗黙の前提により、実際には1箇所（銀座 蔦屋書店内FOAM CONTEMPORARY）のみで
開催されているイベントを、GINZA SIXと蔦屋書店の「複数会場開催」と誤認しかけた。
執筆時の本文確認により訂正済みだが、自動判定では検出できていなかった。

### ② Quality Gate仕様

BLOCKER 6種（開催日不明／会場不明or矛盾未解決／終了済み／情報源矛盾未解決／
重複未処理／Content Richness=boilerplateで例外理由なし）、WARNING 7種
（料金・予約要否・所要時間・アクセス・撮影可否・画像未選定・Content Richness=thin）
で定義した（詳細は§4）。

### ③ Trial記事のPASS／WARNING／BLOCKER判定

**4候補すべてWARNING、BLOCKERなし**（詳細は§5の一覧表）。

### ④ BLOCKERの内容

**該当なし**——ただし③は執筆時の手動訂正がなければBLOCKER相当だった可能性が高いことを明記した（§5参照）。

### ⑤ WARNING一覧

料金未確認（①③④の一部）、予約要否未確認（①③）、所要時間未確認（①）、
アクセス未確認（全4候補）、撮影可否未確認（全4候補）、画像未選定
（4候補ともURLは確認済みだが記事への実際の選定・配置は未実施）。

### ⑥ SNS展開前に人間が確認すべき事項

- ③の会場情報（FOAM CONTEMPORARY＝銀座 蔦屋書店内）を一次情報で最終確認
- 全候補の料金・予約要否・撮影可否——特に③（展覧会）の撮影可否は訴求に影響
- 画像のSNS転用可否——**現状すべて未確認のため、確認なしにSNS投稿へ転用しない**

### ⑦ 画像選定Trialへ進める状態か

**仕様整理までは完了**。実際の画像選定（記事冒頭候補・各イベント候補の決定）は
次工程として着手可能だが、**SNS転用可否が全候補未確認のままのため、SNS投稿を
前提とした選定は許諾確認が先**。note記事内埋め込み（自サイトの記事表示目的）と
SNS外部転用は利用条件が異なりうる点に注意。

### ⑧ 次回以降、この誤認をAI側でどこまで防止できるか

**§1.3の判定ルールをコード実装すれば、機械的な検出は可能**——「複数サイトに同一
タイトル・同一会期の記事がある」こと自体は既存のStory Clustering・重複検知の
仕組みで判定可能であり、そこに「各ページの会場記述を比較し、一致しなければ
BLOCKERとして停止する」ロジックを追加すれば、今回のケースは執筆前に検出できた
可能性が高い。**ただし「会場記述」の抽出自体（本文中のラベル付き表現の識別）は
新たな抽出ロジックが必要**で、既存の`extractStructuredDates.ts`のvenue抽出
（JSON-LDのみ対象）だけでは今回のケース（本文中の自由記述「店内アートスペース
FOAM CONTEMPORARYにて開催」）を拾えない。100%の自動防止は現時点では見込めず、
**「機械的にBLOCKERとして止め、人間に判断を委ねる」設計が現実的**——完全な
自動解決ではなく、誤って見落とすリスクを減らすゲートとして機能させるのが妥当。
